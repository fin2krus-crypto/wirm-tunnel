
# WinRM-tunnel-VPN

Экспериментальный легковесный IPv4-туннель.
Проект реализует полную мимикрию соединений под протокол удалённого администрирования **Windows Remote Management (WinRM over HTTPS, TCP `5986`)** на базе стека **Windows Server 2022/2025 (Schannel + `http.sys`)**.

Состоит из:
- **Сервера:** Linux (`x86_64`) со встроенным TUN-маршрутизатором и машиной состояний `Microsoft-HTTPAPI/2.0`.
- **Клиента:** Android-приложение (`VpnService` + нативное ядро на Go с патченным `uTLS`).

---

## Архитектура и принцип работы

Туннель не использует открытые сигнатуры VPN-протоколов (WireGuard, OpenVPN, SSH) и не оборачивает трафик в подозрительные кастомные заголовки. Передача данных происходит внутри легитимной сессии `WS-Management` поверх TLS 1.2/1.3.

```text
[ Android Client ] 
       │  (uTLS: Schannel Fingerprint, no SNI)
       ▼
 1. TCP SYN ──────────────────────────► [ Linux Server ] (TTL 128, No Timestamps)
 2. TLS Handshake (Schannel Spec) ────► Windows Server 2022 TLS Profile
 3. POST /wsman (NTLM Type 1) ────────► 
    ◄────── 401 Unauthorized (NTLM Type 2 Challenge с AV_PAIR Windows)
 4. POST /wsman (NTLM Type 3 + HMAC) ─► [Проверка HMAC + Replay Protection]
    ◄────── 200 OK (SOAP CreateResponse)
 5. [ Двусторонний IPv4-поток с паддингом под SOAP-фреймы ]
```

## Применённые технологии скрытия и обхода DPI

### 1. Сетевой уровень и OS Fingerprinting (TCP/IP)
- **Linux Server Network Stack Tuning:** С помощью скрипта настройки сервера параметры стека ядра Linux приводятся к значениям Windows Server 2022:
  - Исходящий `IP TTL = 128` (вместо дефолтного для Linux `64`).
  - Полное отключение `TCP Timestamps` (`net.ipv4.tcp_timestamps = 0`), что характерно для стека `http.sys` в современных версиях Windows Server.
  - Включен `TCP Window Scaling` со стандартными для Windows размерами окон.

### 2. TLS-уровень (Эмуляция Windows Schannel)
- **Точный ClientHello (Android):** Использование `uTLS` для формирования сырого TLS `ClientHello` в точности по спецификации Windows Schannel (Windows 11 / Server 2022):
  - **Отсутствие GREASE:** В отличие от браузеров Chrome/BoringSSL и стандартного Android Conscrypt, в Schannel GREASE-значения не применяются.
  - **Отсутствие ChaCha20-Poly1305:** В нативном Schannel приоритет отдан шифрам `TLS_AES_256_GCM_SHA384` и `ECDHE_RSA / ECDHE_ECDSA` с AES-GCM/CBC. Присутствие ChaCha20 в `ClientHello` моментально выдаёт Linux/Android/Go.
  - **Корректная обработка SNI:** При подключении к серверу по прямому IPv4-адресу клиент Schannel в Windows **не передаёт расширение SNI (Server Name Indication)** согласно стандарту RFC 6066 [^1]. Наш клиент строго соблюдает это правило.
  - **ALPN:** Запрещён анонс HTTP/2 (`h2`). Служба WinRM на порту 5986 работает исключительно по протоколу HTTP/1.1.
- **Сертификат Windows Server:** Автоматическая генерация самоподписанного X.509 сертификата со структурой утилиты `New-SelfSignedCertificate`: субъект `CN=WIN-XXXXXX`, KeyUsage (`KeyEncipherment`, `DigitalSignature`), EKU (`Server Authentication`), срок действия — 1 год. Проверка подлинности на клиенте реализована через **SHA-256 Certificate Pinning**.

### 3. Скрытая аутентификация в момент установления соединения (Covert Handshake)
- **Многоэтапный NTLM-хендшейк:**
  - Клиент начинает сессию легитимным запросом `POST /wsman?PSVersion=5.1...` с токеном `NTLMSSP_NEGOTIATE` (Type 1).
  - Сервер возвращает ответ `401 Unauthorized` с динамически сгенерированным `NTLMSSP_CHALLENGE` (Type 2), содержащим корректные структуры `AV_PAIR` (NetBIOS/DNS имена, штамп времени Windows `FILETIME`).
  - В ответе `NTLMSSP_AUTH` (Type 3) клиент встраивает скрытый токен аутентификации:
    $$\text{HMAC-SHA256}(\text{PSK}, \text{ServerChallenge} \parallel \text{Timestamp} \parallel \text{ClientNonce})$$
    Токен дополнен случайным паддингом, за счёт чего размер заголовка байт-в-байт укладывается в нормальное распределение длины реального NTLMv2-ответа Windows.
- **Защита от Replay-атак:** Сервер валидирует временную метку `Timestamp` внутри токена с допустимым окном в $\pm 120$ секунд и привязывает её к разовому `ServerChallenge`. Перехват и повторная отправка запроса цензором не позволят активировать туннель.

### 4. Устойчивость к активному зондированию (Active Probing Resistance)
Любой сетевой сканер, цензор или исследователь, обращающийся к порту `5986` без знания предварительного ключа (PSK), взаимодействует с полноценным эмулятором `Microsoft-HTTPAPI/2.0`:
- **WS-Management Identify (`Test-WSMan`):** Запрос проверки доступности WinRM возвращает легитимный XML-ответ DMTF/WS-Man с полями `ProductVendor: Microsoft Corporation` и версией стека `3.0`.
- **Запросы без авторизации / некорректные пути:** Отдаются стандартные страницы ошибок `http.sys` (`404 Not Found`, `400 Bad Request`) с соответствующими HTML-шаблонами и служебными заголовками.
- **Попытка подбора пароля (Brute-force / Nmap):** Возвращается стандартный цикл `401 Unauthorized` с механизмами `Negotiate`, `Kerberos`, `CredSSP`.

### 5. Транспорт данных и маскировка длин пакетов
- **Отсутствие двойного шифрования:** Поскольку сессия уже изолирована криптографически стойким шифром TLS (AES-256-GCM), инкапсуляция IP-пакетов не использует дополнительное шифрование, что обеспечивает минимальные задержки и низкое энергопотребление на мобильном устройстве.
- **Traffic Framing & Padding:** Мелкие сетевые пакеты (TCP ACK, DNS-запросы) выравниваются паддингом минимум до 256 байт. Это исключает характерную для туннелей бимодальную сигнатуру длин пакетов и имитирует минимальные размеры блоков SOAP-конвертов PowerShell Remoting (PSRP).

## Недостатки и возможные векторы обнаружения цензором

Несмотря на глубокую маскировку TLS и уровня приложений, существуют технические и статистические метрики, по которым квалифицированный наблюдатель с развитыми DPI/ML-комплексами может выявить аномалию:

### 1. Межуровневый диссонанс отпечатков ОС на клиенте (Cross-Layer Fingerprint Mismatch)
- **В чём проблема:** Клиент работает на Android (без root-прав). Нативное ядро приложения формирует идеальный TLS `ClientHello` операционной системы **Windows (Schannel)**. Однако исходящие TCP SYN-пакеты генерируются ядром Linux Android (`TTL = 64`, включены `TCP Timestamps`, специфический порядок TCP Options: `MSS, SACK, TS, NOP, WS`).
- **Как цензор может обнаружить:** Продвинутые DPI сопоставляют пассивный OS-отпечаток TCP (например, алгоритмы `p0f`) и TLS-отпечаток (JA4 / JA3). Если TCP SYN указывает на Linux/Android, а TLS ClientHello утверждает, что это Windows Schannel, сессия помечается как аномальная (инъекция/маскарад).

### 2. Поведенческий анализ профиля трафика (Traffic Flow / Volume Anomaly)
- **В чём проблема:** Протокол WinRM предназначен для системного администрирования (передача команд PowerShell, вывод скриптов, передача небольших конфигурационных файлов). 
- **Как цензор может обнаружить:**
  - **Длительность и симметрия потока:** Непрерывное скачивание больших объёмов данных (видеостриминг, торренты, загрузка ISO) на скорости в десятки мегабит на протяжении нескольких часов нехарактерно для WinRM.
  - **Паттерн Keep-Alive:** Настоящий WinRM в режиме ожидания генерирует периодические длинные опросы (`Receive` pull request раз в 60 секунд) либо закрывает сессию по таймауту. Стабильный дуплексный поток байтов внутри одного HTTP-запроса выбивается из базовой статистики PSRP.

### 3. IP-репутация, геолокация и сетевое окружение
- **В чём проблема:** В корпоративной среде Windows Server с открытым наружу портом WinRM HTTPS (`5986`) практически всегда находится в диапазонах корпоративных сетей или облачных подсетей, имеет обратную PTR-запись, а рядом на том же IP часто открыты порты смежных служб (RDP `3389`, HTTPS `443`, SMB `445`).
- **Как цензор может обнаружить:** Если зарубежный IP-адрес хостинг-провайдера держит открытым исключительно порт `5986` (без других служб экосистемы Windows), трафик на него поступает от мобильного оператора другой страны, а сам IP отсутствует в белых списках корпоративных инфраструктур, ML-классификатор цензора отнесёт хост к категории «прокси/туннель».

### 4. Ограниченность эмуляции PSRP при глубоком зондировании (Deep Stateful Probing)
- **В чём проблема:** Сервер полностью эмулирует фазу WS-Man `Identify`, NTLM-хендшейк и шаг инициализации `Shell Create`. Однако он не содержит полноценного интерпретатора PowerShell.
- **Как цензор может обнаружить:** Если активный зонд цензора попробует после успешной аутентификации передать реальный бинарный PSRP-фрейм команды (например, `Command: Get-Process`), наш сервер воспримет этот бинарный поток как входящий IPv4-пакет интерфейса TUN, не сможет вернуть валидный SOAP-ответ выполнения команды и разорвёт поток.

## Сборка и запуск

Проект собирается автоматически с помощью прилагаемого рабочего процесса **GitHub Actions** (`.github/workflows/build.yml`):
- Статический бинарник сервера для Linux: `dist/winrm-vpn-server`
- Готовое приложение для Android: `dist/winrm-vpn-client.apk`

*Проект создан исключительно в исследовательских целях для тестирования классификаторов трафика и оценки эффективности DPI-систем.*

[^1]: [RFC 6066: Transport Layer Security (TLS) Extensions: Extension Definitions](https://datatracker.ietf.org/doc/html/rfc6066#section-3)
